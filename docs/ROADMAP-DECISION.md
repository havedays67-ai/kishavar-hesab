# تصمیم معماری: آفلاین‌محور تدریجی (Offline-first, phased)

**تصمیم مدیر پروژه — نسخه ۱.۱**

خلاصه در یک خط: **هسته حسابداری را همین حالا آفلاین و قطعی کردم؛ حذف کامل سرور را الان انجام نمی‌دهم و مدل زبانی روی گوشی را «اختیاری با فال‌بک قطعی» می‌گذارم، نه مسیر اصلی.**

این سند پاسخ رسمی به پیشنهاد «تبدیل کامل به اپ آفلاین با حذف سرور» است.

---

## ۱) ارزیابی پیشنهاد: چه چیزی پذیرفته شد و چه چیزی نه

| بند پیشنهاد | تصمیم | دلیل مهندسی |
|---|---|---|
| SQLite محلی با همان اسکیما، مبلغ صحیح، CHECK، ایندکس، مهاجرت نسخه‌دار | ✅ **انجام شد** | `src/lib/engine/localdb.ts`: ۳ مهاجرت، ۱۸ جدول، CHECK و ایندکس کامل + FTS5 برای RAG |
| موتور حسابداری قطعی جدا + تست واحد | ✅ **انجام شد** | `src/lib/engine/accounting.ts` و `money.ts` — **۳۲۶ تست** سبز (`npx vitest run`) |
| هیچ محاسبه‌ای به مدل سپرده نشود | ✅ **انجام شد** | قرارداد JSON جدا؛ مبلغ/تاریخ/اعتبارسنجی در `accounting.ts`، مدل فقط متن را به اسلات تبدیل می‌کند |
| بکاپ رمزنگاری‌شده + بکاپ خودکار + هشدار | ✅ طراحی شد | جدول `settings`/`mutation_log` + فاز ۲ برای فایل رمزنگاری‌شده (AES-GCM با WebCrypto در اپ) |
| Undo و لاگ عملیات | ✅ **انجام شد** | `inverseAction` / `canUndo` + جدول `mutation_log` (قابل واگرد و قابل حسابرسی) |
| خروجی JSON با گرامر اجباری | ✅ **انجام شد** | `assistantJsonSchema()` + `validateAssistantOutput()` — دیتاست هم با همین سنجیده می‌شود |
| مدل ۱ تا ۲ میلیاردی int4 روی گوشی | ⚠️ **پذیرفته با شرط** | فقط به‌عنوان **لایه اختیاری**؛ مسیر تضمین‌شده NLU قطعی است (پایین توضیح داده شده) |
| مدل داخل APK نباشد، دانلود با هش و ادامه پس از قطع | ✅ **انجام شد** | جدول `download_state` با `sha256`، `etag`، `bytes_done` و وضعیت‌ها |
| حذف سرور و PostgreSQL | ⛔ **رد در فاز ۱** | با حذف سرور، گزارش چندساله، بکاپ ابری، چند کاربر و اشتراک خانواده از دست می‌رود و ریسک «از دست رفتن داده» بالا می‌رود. معماری دوحالته می‌شود: آفلاین اصلی + سرور اختیاری برای بکاپ/همگام‌سازی |
| حذف Next.js سمت سرور | ⛔ **رد** | همان کامپوننت‌ها و همان UI در PWA کار می‌کند؛ نگه‌داشتن سرور هزینه نگهداری تقریباً صفر دارد و مسیر «بکاپ و بازیابی» را ممکن می‌کند |
| «یادگیری = آموزش مجدد روی گوشی» | ⛔ **رد** | آموزش روی گوشی با ۶ گیگ رم و باتری محدود، غیرواقعی است. یادگیری = حافظه کاربر + RAG روی داده خودش (که پیاده شده) |
| «حداقل ۲۰۰ تست» | ✅ انجام شد (۳۲۶) | اما تست فقط عدد نیست؛ تست‌ها روی **موتور قطعی و قرارداد** نوشته شده‌اند، نه روی UI |
| آموزش با دو معلم + پالایش + اسپلیت + آستانه ۹۸٪/۱۰۰٪ | ✅ **انجام شد** | اسکریپت دو معلم، اعتبارسنج قطعی مشترک، دیتاست پایه ۲۴۱ نمونه تمیز و ۸۶۹ نمونه تولیدی با ۰ خطا |

## ۲) واقعیت فنی مدل روی گوشی (بدون خوش‌بینی)

| موضوع | واقعیت | نتیجه برای طراحی |
|---|---|---|
| حجم مدل ۱.۷B در int4 | حدود ۱ تا ۱.۳ گیگابایت روی دیسک | دانلود اجباری در APK نیست؛ درست است |
| RAM اجرا | حدود ۰.۸ تا ۱.۵ گیگابایت اضافه بر اپ | روی گوشی ۶ گیگ با اپ‌های باز، خطر OOM واقعی است |
| GPU موبایل | به درایور OpenCL و سازنده بستگی دارد؛ روی اندروید ۸ همه‌جا قابل اتکا نیست | باید CPU fallback داشته باشیم |
| سرعت CPU | حدود چند توکن در ثانیه (دستگاه‌ضعیف کندتر) | پاسخ باید کوتاه باشد؛ هرگز چت طولانی |
| کیفیت فارسی مدل ۱B | برای «تولید متن» ضعیف، برای «تبدیل به JSON با اسکیمای بسته» قابل قبول | مدل فقط NLU می‌کند، نه حسابداری و نه گزارش عددی |
| MediaPipe LLM / llama.cpp | هر دو ممکن؛ MediaPipe راحت‌تر ولی محدود به مدل‌های پشتیبانی‌شده؛ llama.cpp جهانی و اندروید ۸ را هم می‌گیرد | **llama.cpp مسیر اصلی، MediaPipe مسیر سبک** |

**نتیجه قطعی:** روی این کلاس دستگاه، «هوش مصنوعی روی گوشی» باید **بهبود تجربه** باشد، نه تکیه‌گاه دقت. تکیه‌گاه دقت، همان NLU قطعی + موتور حسابداری است که همین حالا تست‌شده و آفلاین‌شدنی است.

### انتخاب مدل (پیشنهاد با دلیل، نه ادعای بنچمارک)
| گزینه | مزیت | ریسک | رتبه |
|---|---|---|---|
| **Qwen3-1.7B-Instruct (Q4_K_M, llama.cpp)** | پیروی خوب از JSON، پوشش خط عربی/فارسی، اکوسیستم GGUF، اجرا روی اندروید ۸ با CPU | RAM بالاتر، سرعت CPU متوسط | 🥇 مسیر اصلی |
| **Gemma-3-1B-it (int4، MediaPipe `.task`)** | سبک‌تر، یکپارچگی ساده با اندروید | پشتیبانی فارسی/JSON ضعیف‌تر؛ وابستگی به نسخه‌های پشتیبانی‌شده | 🥈 مسیر سبک |
| Qwen2.5-1.5B-Instruct | بالغ و پایدار | کمی قدیمی‌تر، JSON سخت‌گیرانه ضعیف‌تر از Qwen3 | 🥉 جایگزین |
| SmolLM2-1.7B | سریع | فارسی/عربی ضعیف | ❌ |

اعداد نهایی **باید** با `training/eval_model.py`‑style روی test شما اندازه‌گیری شود؛ در این محیط GPU نیست و هیچ عددی ادعا نمی‌کنم.

## ۳) پاسخ به ایده شما: «ایجنت محلی + دیتاست از من و کلاد»

**پاسخ: بله، همین بهترین مسیر است — با سه شرط.** ایجنت شما باید «هماهنگ‌کننده» باشد، نه «منبع حقیقت».

1. **منبع حقیقت، کد است نه مدل.** قرارداد JSON، موتور حسابداری و اعتبارسنج دیتاست در ریپو هستند (`src/lib/engine/*`, `scripts/validate-dataset.ts`). هر نمونه‌ای که معلم‌ها (Claude/DeepSeek/هر مدل دیگر) تولید کنند، **باید** از همین اعتبارسنج رد شود؛ در غیر این صورت دور ریخته می‌شود. الگوی «توافق هر دو معلم» هم در `training/generate_teachers.py` پیاده شده است.
2. **دو نوع دیتاست را قاطی نکنید.**
   - دیتاست «نیت→اسلات» (همین کار): برای fine-tune مدل.
   - داده «مزرعه من» (زمین، هزینه، چک…): **هرگز** داخل آموزش نمی‌رود؛ با RAG و حافظه در اپ خوانده می‌شود. اگر این را آموزش بدهید، مدل اعداد قدیمی را از حافظه بازتولید می‌کند و «توهم عددی» می‌سازید.
3. **کلیدها و اتصال‌ها سمت سرور بمانند.** اتصال ایجنت به گوشی و سرویس‌های ابری برای «ارزیابی، گرفتن بنچمارک، آپلود APK/مدل» عالی است؛ اما هیچ کلیدی داخل اپ یا ریپو نرود و ایجنت نباید بدون تأیید انسان روی داده واقعی بنویسد.

**پیشنهاد بهتر من در یک جمله:** خروجی کار ایجنت را به «اسکریپت‌های تکرارپذیر + گزارش JSON» تبدیل کنیم (همین شد: `training/*`, `scripts/*`)، تا هر بار آموزش/ارزیابی قابل بازتولید و قابل حسابرسی باشد — نه یک چت یک‌بارمصرف.

## ۵) کارهایی که **فقط شما** می‌توانید انجام دهید

1. **آموزش روی GPU** (من در این محیط GPU ندارم):
   ```bash
   npx tsx scripts/gen-dataset.ts
   npx tsx scripts/validate-dataset.ts training/data/*.jsonl
   export ANTHROPIC_API_KEY=... DEEPSEEK_API_KEY=...
   python3 training/generate_teachers.py --per-intent 150     # اختیاری: بزرگ‌کردن دیتاست
   python3 training/train_qlora.py --model Qwen/Qwen3-1.7B --data training/data/teachers
   ```
   آستانه: intent ≥ ۹۸٪، فیلدها ≥ ۹۸٪، JSON معتبر ۱۰۰٪. اگر رد شد، `eval_report.json` را بفرستید تا دیتای هدفمند اضافه کنم.
2. **استخراج و میزبانی مدل**: `bash training/export_gguf.sh` سپس فایل `kishavar-q4_k_m.gguf` + `sha256` را جایی (S3/GitHub Release) بگذارید و URL را به من بدهید تا در جدول `download_state` ثبت شود.
3. **کلید امضای Release اندروید** (Secrets مخزن: `KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD`).
4. **بنچمارک روی گوشی خودتان**: نصب APK، اجرای ۲۰ دستور نمونه، ثبت «زمان پاسخ» و «دقت» با `docs/AGENT-HANDOFF.md`.
5. **تصمیم درباره نگه‌داشتن سرور**: پیشنهاد من نگه‌داشتن به‌عنوان بکاپ/همگام‌سازی اختیاری است؛ اگر اصرار به حذف دارید، فقط فاز ۲ و ۳ را کافی می‌دانم و سرور را خاموش می‌کنیم، اما بکاپ رمزنگاری‌شده باید اول آماده شود.

## ۶) ریسک‌ها و پاسخ
- **توهم عددی** ← پاسخ: هیچ عددی از مدل پذیرفته نمی‌شود؛ اعتبارسنج قطعی + پیش‌نمایش + تأیید.
- **OOM روی ۶ گیگ** ← پاسخ: سه‌سطحی اجرا و پیش‌فرض NLU؛ مدل دانلود نمی‌شود مگر کاربر بخواهد.
- **از دست رفتن داده** ← پاسخ: بکاپ اجباری با هشدار + `mutation_log` + `uuid` برای همگام‌سازی بعدی.
- **نشت کلید** ← پاسخ: هیچ کلیدی در ریپو/اپ نیست؛ اعتبارسنجی CI.
- **دیتاست آلوده** ← پاسخ: پالایش دو مرحله‌ای + توافق دو معلم + تست قرارداد.
