## بخش اول — دستیار کنشگر (Agent)

### ۱) اصل طراحی: مدل «برنامه» می‌دهد، برنامه «اجرا» می‌کند

```
کاربر: «این رسید رو برای پرداخت علی بذار»
        │
        ▼
مدل ──► JSON: {"actions":[{"type":"receipt.open","target":"party-payment","id":"pay-..."}]}
        │
        ▼
اعتبارسنج (actions.ts) ──► allowlist + فیلدهای مجاز + سقف مبلغ + تأیید
        │
        ▼
اجراکنندهٔ برنامه در برنامه (توابع همان صفحه) ──► تغییر واقعی + ثبت در گزارش
        │
        ▼
پاسخ کوتاه به کاربر
```

مدل هیچ‌گاه کد اجرا نمی‌کند، فایل باز نمی‌کند، به شبکه دسترسی ندارد و
هیچ کلید یا دادهٔ دفتر را نمی‌بیند. حداکثر کاری که می‌کند پیشنهاد یک ساختار
محدود است.

### ۲) فهرست بستهٔ کنش‌ها (نسخهٔ فعلی)

| کنش | کار | تأیید لازم |
|---|---|---|
| `navigate` | رفتن به صفحه | خیر |
| `party.create` | ثبت طرف‌حساب | خیر (مبلغ ≤ سقف) |
| `party.payment.add` | ثبت پرداخت | خیر |
| `entry.add` | ثبت درآمد/هزینه | خیر |
| `receipt.open` | باز کردن رسیدهای یک رکورد | خیر |
| `record.update` | ویرایش یک فیلد مشخص | **بله** |
| `document.print` | آماده‌سازی چاپ | خیر |
| `answer` | فقط پاسخ متنی | خیر |

**عمداً وجود ندارد:** حذف رکورد، اجرای کد، باز کردن URL، ارسال پیام به بیرون،
دسترسی به فایل‌های دستگاه. این‌ها سطح حمله می‌سازند و در نسخهٔ اول لازم نیستند.

### ۳) قواعد سختِ اعتبارسنج

- حداکثر **۳ کنش** در هر نوبت.
- فیلد ناشناخته = رد کل کنش (نه نادیده گرفتن).
- متن‌ها: بدون `< > { }`، بدون `javascript:`، بدون URL، حداکثر ۱۶۰ نویسه.
- مبلغ: عدد مثبت و ≤ ۵ میلیارد تومان؛ مبلغ از خود مدل ممنوع (پرامپت + اعتبارسنج).
- شناسه‌ها باید با رکورد موجود بخوانند؛ در اجرا اگر پیدا نشد، کنش لغو و علت گفته می‌شود.
- JSON خراب = **هیچ** کنشی اجرا نمی‌شود (fail-closed).

### ۴) حلقهٔ تأیید و بازگشت

1. پیش‌نمایش فارسی هر کنش (`describeAction`).
2. برای `record.update` دکمهٔ «تأیید میکنم» الزامی است.
3. هر اجرا در «گزارش کنش‌ها» ثبت می‌شود: زمان، کنش، خلاصه، نتیجه.
4. برای کنش‌های مالی، امکان **لغو** تا ۳۰ ثانیه (undo) نگه داشته می‌شود.
5. اگر مدل مطمئن نیست، `actions: []` و `question` می‌فرستد؛ هیچ تغییری رخ نمی‌دهد.

### ۵) چرا این «دسترسی کامل» امن است

- دسترسی کامل به **همان برنامه** = همان توابعی که کاربر با دکمه‌ها صدا می‌زند؛
  نه بیشتر. هر کنش از همان مسیر اعتبارسنجی و همان ذخیره‌سازی رد می‌شود.
- مدل هیچ راهی به حافظهٔ دستگاه، دوربین، فایل‌ها یا شبکه ندارد.
- سوءاستفادهٔ پرامپت (prompt injection) فقط می‌تواند کنش‌های مجاز را پیشنهاد دهد؛
  حذف و ویرایش بدون تأیید کاربر غیرممکن است.

## بخش دوم — مشاور کشت: «چه چیزی، کِی، با چه آبی، چقدر سود»

### ۶) زنجیرهٔ تصمیم (۶ لایه)

```
۱) پروفایل مزرعه: منطقه، اقلیم، مساحت، خاک، شوری، منبع آب، بودجه
۲) تقویم کشت منطقه: پنجرهٔ کاشت/برداشت برای هر محصول (جدول کارشناسی)
۳) تراز آب: نیاز (mm→m³) در برابر آب در دسترس
۴) ریسک‌ها: سرما/گرما/بارش، شوری، خاک نامناسب، کمبود بودجه
۵) اقتصاد: هزینه × مساحت، درآمد = عملکرد × قیمت × مساحت، سود = بازه
۶) روایت مدل: فقط توضیح و مقایسه؛ هیچ عددی از خودش نمی‌سازد
```

پیاده‌سازی: `planCrop()` و `rankCrops()` برای ۸ محصول (گندم آبی/دیم، جو، کلزا،
ذرت علوفه‌ای، یونجه، پنبه، چغندرقند) با امتیازدهی وزنی و «عامل بازدارنده».

### ۷) داده‌های لازم و منبع هرکدام

| داده | منبع | تازگی |
|---|---|---|
| اقلیم و پنجرهٔ کاشت | جدول کارشناسی داخلی (قابل ویرایش) | سالانه |
| پیش‌بینی ۱۰ روزه | Open-Meteo (رایگان، بدون کلید) | هر ۳ ساعت |
| نرمال اقلیمی منطقه | Open-Meteo Archive / سازمان هواشناسی | سالانه |
| شوری و بافت خاک | آزمایش خاک کاربر (اولویت) یا نقشهٔ خاک منطقه | فصلی |
| آب در دسترس | ورود کاربر (حجم چاه/ساعت پمپاژ) | فصلی |
| قیمت محصول | جست‌وجوی Jina + بولتن‌های رسمی | روزانه |
| تعرفه/بیمه | جست‌وجو + اعلامیهٔ استان | فصلی |

هیچ‌کدام «از حافظهٔ مدل» گرفته نمی‌شود. اگر داده نبود، `questions` پر می‌شود
و `confidence` پایین می‌آید.

### ۸) امتیازدهی و صداقت عددی

- امتیاز ۰–۱۰۰ از وزن‌های ثابت: آب ۳۰، اقلیم ۲۵، هوا ۲۵، شوری ۲۰، خاک ۱۵، بودجه ۱۵.
- وضعیت هر عامل: خوب=۱، هشدار=۰٫۵، نامعلوم=۰٫۴، بد=۰.
- **عامل بازدارنده** (دیم برای محصول پرآب، شوری بیش از ۱٫۵ برابر تحمل) امتیاز را
  زیر ۴۰ می‌آورد تا هیچ جدول خوبی آن را جبران نکند.
- اقتصاد همیشه **بازه** است؛ هرگز «سود قطعی» گفته نمی‌شود.
- خروجی همیشه شامل «دادهٔ زندهٔ لازم» است تا کاربر بداند عدد بازار دستی است.

### ۹) پرسش‌های روشن‌کننده (حداکثر ۲)

- آب: «در کل فصل چند متر مکعب آب دارید؟»
- شوری: «EC خاک را می‌دانید؟»
- هوا: «اجازهٔ جست‌وجوی پیش‌بینی ۱۰ روزه را می‌دهید؟»
- بودجه: «بودجهٔ این فصل چقدر است؟»

اگر کاربر جواب نداد، با فرض محافظه‌کارانه ادامه می‌دهد و **صریح** می‌گوید
«بر اساس فرض X»؛ هرگز فرض را پنهان نمی‌کند.

### ۱۰) مصرف توکن در مشاور کشت

| مرحله | هزینه |
|---|---|
| محاسبهٔ تراز آب و امتیاز | ۰ توکن (محلی) |
| پیش‌بینی هوا | ۰ توکن (HTTP رایگان) |
| قیمت بازار | ۱ جست‌وجو + ۱ فراخوانی کوتاه |
| توضیح و مقایسهٔ نهایی | ۱ فراخوانی، حداکثر ۹۰۰ توکن |

یعنی گران‌ترین بخش (استدلال) فقط یک‌بار و در پایان انجام می‌شود؛ نه در هر پیام.

### ۱۱) مثال خروجی

```
گندم آبی: مناسب (امتیاز ۸۲ از ۱۰۰)
پنجرهٔ کاشت: مهر تا نیمهٔ آبان
آب: نیاز ۲۷٬۵۰۰ متر مکعب — در دسترس ۲۵٬۰۰۰ (کمبود ۲٬۵۰۰)
سود برآوردی: ۱۲۰ تا ۲۱۰ میلیون تومان (بازهٔ راهنما)
ریسک‌ها: کمبود آب
برای دقیق‌تر شدن: در کل فصل چند متر مکعب آب دارید؟
دادهٔ زندهٔ لازم: قیمت روز بازار، پیش‌بینی ۱۰ روزهٔ هوا
```

## ۱۲) اتصال به ابر (وضعیت)

- دروازهٔ ابری و جابه‌جایی ۵ کلید ساخته و تست شد.
- **مانع فعلی:** کلیدهای `dahl_…` روی دامنه‌های عمومی GLM (z.ai / bigmodel) معتبر
  نیستند؛ آدرس پایهٔ همان سرویس لازم است. با گرفتن `Base URL` و نام مدل، فقط
  `UPSTREAM_URL` و `AI_MODEL` در Worker تنظیم می‌شود و اتصال کامل می‌شود.
- دامنهٔ `tivachat-vflash-ai.ir` در همین حساب Cloudflare فعال است؛ Worker جدید
  می‌تواند روی `ai.tivachat-vflash-ai.ir` بنشیند بدون دست زدن به
  `chat.tivachat-vflash-ai.ir` و `kishavar.tivachat-vflash-ai.ir`.

## ۱۳) نقشهٔ اجرا

| فاز | کار | وضعیت |
|---|---|---|
| ۱ | قرارداد کنش‌ها + اعتبارسنج + تست | ✅ |
| ۲ | برنامه‌ریز کشت + تست | ✅ |
| ۳ | اجراکنندهٔ کنش در برنامه (اتصال به state صفحات) | ⏳ |
| ۴ | اتصال Worker (نیاز به Base URL) | ⏳ |
| ۵ | هوا (Open-Meteo) + قیمت (Jina) + کش | ⏳ |

معیار پذیرش فاز ۳:
- «برای علی ۲ میلیون پرداخت ثبت کن» → پرداخت واقعی + رسید باز شود.
- «شمارهٔ علی رو عوض کن» → فقط با تأیید.
- «همهٔ بدهکارها رو پاک کن» → رد شود (کنش حذف وجود ندارد).
- هیچ کنشی بدون رکورد موجود اجرا نشود.
